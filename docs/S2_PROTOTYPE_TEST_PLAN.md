# S2 — خطة النموذج الأولي والاختبارات

## 1. الغرض

إثبات الحد الأدنى من صلاحية المعمارية المعتمدة دون إنشاء خدمة سحابية ودون بيانات حقيقية. النموذج لا يبني شاشات ولا ينفذ وظائف المراحل S3–S8.

## 2. مكونات النموذج

- `prototype/s2_local_architecture/core.py`: نموذج SQLite لعلاقات D1، قائمة المستخدمين، التزامن، التدقيق والتصدير.
- `prototype/s2_local_architecture/schema.sql`: نسخة SQL للمراجعة وخطة migrations المستقبلية.
- `prototype/worker_auth/auth.mjs`: تحقق Firebase ID Token باستخدام Web Crypto، واختيار المفتاح حسب `kid`، وcache حسب `max-age`، وفشل مغلق.
- `tests/test_s2_architecture_prototype.py`: اختبارات البيانات والتفويض والتصدير.
- `tests/test_worker_auth.mjs`: اختبارات التوقيع والمفاتيح والمطالبات وقائمة السماح والفشل المغلق.
- `scripts/validate_s2.py`: مدقق محلي حتمي بلا مكتبات خارجية.

## 3. البيانات الوهمية

يستخدم النموذج فقط:

- `uid-person-1` و`uid-person-2`.
- `client-001` باسم «عميل وهمي».
- `work-001` وعناوين وهمية.
- مفاتيح RSA تولد داخل الاختبار ولا تحفظ.
- استجابة وهمية لمفاتيح Google؛ لا يجري اتصال حقيقي بـFirebase.

## 4. حالات اختبار البيانات

| ID | الحالة | المتوقع |
|---|---|---|
| S2-P01 | الشخص الأول ينشئ، والثاني يقرأ ويعدل لاحقًا | نجاح وتسجيل UID الثاني |
| S2-P02 | UID ثالث يحاول قراءة البيانات | رفض `AuthorizationError` |
| S2-P03 | تحديث بإصدار قديم | رفض `ConflictError` |
| S2-P04 | تعديل سجل التدقيق | رفض من قاعدة البيانات |
| S2-P05 | حذف سجل التدقيق | رفض من قاعدة البيانات |
| S2-P06 | تصدير JSON ثم استعادة | تطابق السجل والبيانات |
| S2-P07 | تصدير SQL | وجود schema والصفوف |
| S2-P08 | فحص schema لـFR-027 | عدم وجود file/blob/attachment |

تنفذ حالات البيانات في 7 اختبارات Python؛ يجمع اختبار append-only حالتي التعديل والحذف.

## 5. حالات اختبار Firebase ID Token

| ID | الحالة | المتوقع |
|---|---|---|
| S2-A01 | رمز RS256 صحيح وUID مجهز | قبول |
| S2-A02 | رمز صحيح لكن UID غير مجهز | رفض |
| S2-A03 | `kid` يطابق أحد مفتاحين وcache صالح | اختيار المفتاح الصحيح وعدم إعادة الجلب قبل `max-age` |
| S2-A04 | انتهاء `max-age` | إعادة جلب المفاتيح |
| S2-A05 | `kid` مفقود أو غير معروف | رفض |
| S2-A06 | `auth_time` مفقود أو في المستقبل | رفض |
| S2-A07 | `iss` خاطئ | رفض |
| S2-A08 | `alg` غير RS256 | رفض قبل استخدام المفتاح |
| S2-A09 | `sub` مفقود أو فارغ | رفض |
| S2-A10 | payload معدل دون إعادة توقيع | رفض التوقيع |
| S2-A11 | رمز منتهي أو `iat` مستقبلي أو audience خاطئ | رفض |
| S2-A12 | فشل الشبكة أو HTTP أو غياب `max-age` | رفض Fail closed |

تنفذ هذه الحالات في 11 اختبار Node؛ بعض الاختبارات تغطي أكثر من قيمة سلبية داخل الحالة الواحدة.

## 6. أوامر التشغيل

```bash
python scripts/validate_s2.py
```

وفي CI:

```bash
python scripts/reconstruct_requirements.py
python scripts/validate_foundation.py
python scripts/validate_s2.py
```

## 7. معايير النجاح

- 7 اختبارات Python ناجحة.
- 11 اختبار Node ناجحًا.
- `S2 LOCAL VALIDATION: PASS`.
- فحوص S1 ناجحة في نفس Pull Request.
- ADR بحالة `Accepted` بعد الاعتماد الصريح، ووجود D-006.
- وجود قاعدة هللات صحيحة ومنع floating point.
- عدم وجود بيانات أو أسرار حقيقية.

## 8. ما لا يثبته النموذج

- الأداء الحقيقي ضمن حد CPU على Cloudflare Workers.
- اتصال Firebase أو D1 حقيقي.
- استجابة endpoint Google الحقيقية أو تدوير المفاتيح الفعلي؛ النموذج يختبر المنطق عبر mock.
- توافر الخدمات أو مناطقها أو latency.
- منع تجاوز Worker داخل deployment فعلي.
- استعادة D1 السحابية وTime Travel.
- واجهة المستخدم أو وظائف الأعمال الكاملة.

هذه البنود ليست ادعاءات نجاح في S2، بل مخاطر واختبارات لاحقة صريحة تتطلب موافقة مستقلة قبل إنشاء أي خدمة.
