# قواعد المشروع الملزمة

## أولوية المراجع

1. `docs/APPROVED_REQUIREMENTS.docx`.
2. `docs/DECISION_LOG.md` للقرارات اللاحقة المؤرخة والمعتمدة.
3. `docs/TRACEABILITY_MATRIX.md` لتوزيع المسؤوليات والاختبارات.
4. ملفات المرحلة وPull Request الخاصة بها.

لا يجوز لجلسة أو مساهم تغيير قاعدة معتمدة بصمت. أي تعارض يوقف التنفيذ ويُسجل كقرار مطلوب. البنود غير المحسومة في سجل القرارات لا تتحول إلى قواعد تنفيذية قبل اعتمادها.

## إدارة الفروع والتغييرات

- `main` يمثل آخر نسخة معتمدة فقط.
- كل مرحلة أو إصلاح في فرع مستقل.
- الدمج عبر Pull Request بعد التحقق.
- لا Force Push ولا إعادة كتابة لتاريخ `main`.
- رسائل commits تصف التغيير الحقيقي.
- يجب تحديث `PROJECT_STATE.md` في كل Pull Request مرحلي.
- كل أثر حاكم يجب اختباره من نسخة نظيفة قبل الدمج، ثم من `main` بعد الدمج.

## حدود البيانات

- GitHub للكود والوثائق الفنية والبيانات الوهمية فقط.
- يمنع رفع أسماء العملاء الحقيقية، أرقام التواصل، ملفات الأبحاث، كلمات المرور، الرموز، مفاتيح الخدمات، ملفات البيئة أو نسخ قواعد البيانات.
- أي أمثلة اختبارية تستخدم أسماء وقيمًا مصطنعة بوضوح.

## شرط صفر تكلفة

لا تعتمد تقنية قبل توثيق: الخطة المجانية، الحاجة إلى بطاقة، الحصص، سلوك تجاوزها، مخاطر تغير الخطة، وطريقة التصدير والنقل. لا يتم تفعيل فوترة أو خدمة مدفوعة دون قرار جديد صريح من المستخدم.

## الموافقات الحساسة المعتمدة

- تعديل سعر العمل أو إلغاء أو أرشفة سجل العمل يحتاج موافقة الطرفين وفق `P-05`.
- موافقة الطرفين تعني موافقتين من الحسابين المختلفين؛ لا تُعد موافقة مقدم الطلب موافقة ثانية على طلبه نفسه.
- لا حذف نهائي للسجلات المالية أو التنفيذية.
- يجب حفظ السابق والجديد والسبب والطالب والموافق والتاريخ عند تعديل السعر، وحفظ طلب الإلغاء أو الأرشفة واعتماده.
- `Q-001`: لا يجوز افتراض آلية اعتماد تغيير النسبة الاستثنائية قبل حسمها.
- `Q-002`: لا يجوز افتراض آلية تصحيح أو إلغاء دفعة سابقة قبل حسمها.
- `Q-003`: لا يجوز افتراض إقفال التسويات أو إعادة فتحها قبل حسم الحاجة والآلية.

## صدق التقارير

لا يُعلن النجاح إلا بناء على فحص منفذ فعليًا. تُذكر الإخفاقات والحدود كما هي، ولا تُخفى تحت وصف مثل «جاهز» أو «يعمل».
