# ADR-001 — معمارية التشغيل المجانية

- الحالة: **Proposed**
- التاريخ: 2026-08-03
- أصحاب القرار: المستخدمان، بعد عرض S2
- Issue: #1

## السياق

التطبيق خاص لشخصين، ويحتاج بيانات مركزية قابلة للتتبع، هوية منفصلة، عملًا في أوقات مختلفة، سجل تدقيق، نسخًا واستعادة، وعدم تخزين ملفات الأعمال. الضابط الأعلى هو صفر تكلفة إلزامية، بلا بطاقة أو فوترة تلقائية.

## القرار المقترح

اعتماد التكوين الآتي بعد موافقة المستخدم الصريحة:

- Cloudflare Workers Free لتقديم API والتحقق من التفويض.
- Static Assets/Pages على Cloudflare للواجهة.
- Cloudflare D1 Free لقاعدة بيانات SQL.
- Firebase Authentication Spark للمصادقة فقط.
- حسابان إداريان فقط، مع تعطيل إنشاء/حذف الحساب من المستخدم النهائي.
- تحقق JWT داخل Worker، ثم قائمة سماح UID داخل D1.
- SQL migrations وSQL/JSON export لتقليل الارتباط بالمزود.
- لا Cloudflare Zero Trust، ولا Firebase Blaze، ولا تخزين ملفات العمل.

## الأسباب

- إثبات رسمي مباشر لعدم الحاجة إلى بطاقة في Cloudflare Workers وFirebase Spark.
- سلوك hard-stop/error عند تجاوز حصص Workers/D1 Free بدل رسوم تلقائية.
- D1 علائقي بدلالات SQLite، ويدعم مفاتيح أجنبية وتصدير SQL وTime Travel قصيرًا.
- Firebase يعالج كلمات المرور والجلسات بدل تنفيذ مصادقة مخصصة عالية المخاطر.
- البيانات التشغيلية مستقلة عن مزود الهوية وقابلة للنقل.

## البدائل المدروسة

- Firebase متكامل: بديل ثانٍ صالح مشروط، لكنه أضعف في SQL والتصدير المدار المجاني.
- Supabase Free: مرفوض بسبب توقف الخمول بعد أسبوع.
- Appwrite Cloud Free: مرفوض بسبب توقف الخمول، وخطر حذف المشروع المتوقف، وعدم وجود backup مجاني.
- Apps Script/Sheets: مرفوض بسبب قيود الهوية الدقيقة وسلامة البيانات.
- Cloudflare Zero Trust Access: مستبعد لأنه يطلب بيانات دفع في الإعداد حتى على Free.

## النتائج الإيجابية

- تكلفة إلزامية صفرية في حدود الخطط المختارة.
- هوية منفصلة وتفويض دقيق لشخصين.
- نموذج بيانات علائقي ملائم للعمليات المالية والتاريخية.
- تصدير SQL مفتوح واستعادة قابلة للاختبار.

## النتائج السلبية

- تكامل مزودين.
- ضرورة التحقق من JWT داخل حد CPU المجاني.
- لا SLA على الخطط المجانية.
- النسخ الخارجي يحتاج إجراءً تشغيليًا يدويًا ما لم يعتمد لاحقًا حل مجاني آخر.

## شروط القبول قبل تحويل الحالة إلى Accepted

1. موافقة المستخدم الصريحة على البديل المقترح.
2. تحديث `docs/DECISION_LOG.md` بقرار D مؤرخ.
3. إعادة تشغيل اختبارات S1 وS2 على نفس الفرع.
4. اكتمال المراجعة الذاتية.
5. مراجعة مستقلة في جلسة الإشراف العام قبل الدمج.
