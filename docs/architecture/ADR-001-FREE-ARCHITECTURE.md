# ADR-001 — معمارية التشغيل المجانية

- الحالة: **Accepted**
- التاريخ: 2026-08-03
- صاحب الاعتماد: المستخدم، باعتماد صريح مؤرخ في محادثة S2
- Issue: #1
- القرار المسجل: D-006

## السياق

التطبيق خاص لشخصين، ويحتاج بيانات مركزية قابلة للتتبع، وهوية منفصلة، وعملًا في أوقات مختلفة، وسجل تدقيق، ونسخًا واستعادة، وعدم تخزين ملفات الأعمال. الضابط الأعلى هو صفر تكلفة إلزامية، بلا بطاقة أو فوترة تلقائية.

## القرار المعتمد

- Cloudflare Workers Free لتقديم API والتحقق من المصادقة والتفويض.
- **Cloudflare Workers Static Assets** بوصفها استضافة الواجهة الأساسية المعتمدة.
- Cloudflare D1 Free لقاعدة بيانات SQL.
- Firebase Authentication Spark للمصادقة فقط.
- طريقة الدخول المعتمدة: **Email/Password** لحسابين ينشئهما المشرف فقط.
- تعطيل self-sign-up وحذف الحساب من المستخدم النهائي.
- تعطيل Phone/SMS وAnonymous وأي مزود تسجيل دخول آخر؛ لا يفعّل مزود جديد دون قرار لاحق.
- البداية على نطاق Cloudflare المجاني `workers.dev`، ولا يعد شراء نطاق أو ربط نطاق مدفوع شرطًا للتشغيل.
- Cloudflare Pages ليس الاستضافة الأساسية؛ يبقى بديلًا احتياطيًا لا يستخدم إلا بقرار معماري لاحق.
- تحقق Firebase ID Token داخل Worker، ثم قائمة سماح UID داخل D1 لا تحتوي إلا الشخصين.
- SQL migrations وتصدير SQL وJSON لتقليل الارتباط بالمزود.
- لا Cloudflare Zero Trust، ولا Firebase Blaze، ولا Billing Account، ولا وسيلة دفع.
- لا تخزين لملفات الأعمال.
- لا إنشاء خدمة سحابية فعلية دون موافقة مستقلة.

## حد المصادقة والتفويض

كل مسار API خاص يعمل بوضع **Fail closed**. لا تنفذ أي قراءة أو كتابة قبل نجاح جميع الخطوات الآتية:

1. قبول `alg=RS256` فقط.
2. اشتراط `kid` غير فارغ.
3. جلب شهادات X.509 العامة من endpoint Firebase الرسمي.
4. اختيار الشهادة التي يطابق معرفها `kid` تحديدًا، واستخراج المفتاح العام المطابق واستخدامه للتحقق من التوقيع.
5. تخزين الشهادات مؤقتًا وفق `Cache-Control: max-age`، وتحديثها عند انتهاء الصلاحية أو ظهور `kid` جديد.
6. التحقق من `aud` و`iss` و`exp` و`iat` و`auth_time` و`sub`، وأن `sub` سلسلة غير فارغة.
7. مطابقة `sub` بقائمة السماح للشخصين داخل D1.

أي فشل في الشبكة أو جلب الشهادة أو المطابقة أو استخراج المفتاح أو التوقيع أو المطالبات أو قائمة السماح يؤدي إلى رفض الطلب. لا يوجد fallback أو guest mode يسمح بتجاوز Worker.

تربط D1 بالـWorker من خلال binding داخلي فقط. لا تعرض D1 مباشرة، ولا تمنح الواجهة الثابتة بيانات اعتماد لها، ولا يوجد مسار API يتجاوز طبقة Worker.

المصدر الرسمي الحاكم للتحقق من Firebase ID Token:
https://firebase.google.com/docs/auth/admin/verify-id-tokens

## قيد الحسابين داخل D1

- لا يسمح جدول `app_users` بأكثر من مستخدمين نشطين.
- لا يسمح بتكرار الدور النشط `person_1` أو `person_2`.
- التهيئة الأولى تستخدم `INSERT` ذريًا ولا تستخدم `INSERT OR REPLACE`.
- إعادة التهيئة بالزوج نفسه idempotent، أما استبدال أي UID فيحتاج migration إدارية مستقلة ومراجعة، ولا يتم ضمن دالة provisioning العامة.
- `prototype/s2_local_architecture/schema.sql` هو مصدر المخطط التنفيذي الوحيد للنموذج، ويقرأه `core.py` مباشرة.

## قاعدة القيم المالية

كل مبلغ مالي يخزن ويحسب كعدد صحيح من **الهللات** داخل `INTEGER`، مع منع `REAL` و`FLOAT` و`DOUBLE` ومنع الاعتماد على floating point. يجب أن تكون القيم والنتائج الوسيطة ضمن مجال JavaScript الآمن للأعداد الصحيحة. التفاصيل الحاكمة في:

`docs/architecture/FINANCIAL_INTEGER_RULE.md`

لا تعتمد S2 قاعدة تقريب للنسب؛ تسجل قاعدة التقريب كبند يجب حسمه في المرحلة المالية قبل تنفيذ الحسابات ذات الكسور.

## بوابة CPU الإلزامية قبل تنفيذ S3

حد Workers Free الحاكم هو **10ms CPU لكل استدعاء**. بعد موافقة مستقلة على إنشاء بيئة تجريبية مجانية، تكون أول بوابة تقنية في S3 هي قياس تحقق Firebase ID Token فعليًا على Workers Free، بما يشمل جلب الشهادة عند cache miss، واستخراج المفتاح، والتحقق من RS256، والتحقق من المطالبات وقائمة السماح.

إذا أظهرت الاختبارات المتكررة تجاوز حد Workers Free أو إنهاء الاستدعاءات بسبب CPU بصورة قابلة لإعادة الإنتاج:

1. يتوقف تنفيذ S3 فورًا ولا يبنى فوق مسار غير صالح.
2. تعاد المسألة إلى بوابة القرار المعماري، أو يختار المستخدم بديلًا مجانيًا موثقًا من بدائل S2.
3. يمنع التحويل إلى Workers Paid، أو تفعيل Billing، أو ربط بطاقة لمعالجة المشكلة.

هذه البوابة مانعة وليست ملاحظة أداء اختيارية.

المصدر الرسمي لحدود Workers Free:
https://developers.cloudflare.com/workers/platform/limits/

## الأسباب

- التكوين المختار يعمل ضمن خطط مجانية دون بطاقة أو Billing Account في النطاق المعتمد.
- طلبات Static Assets مجانية وغير محدودة ضمن وصف الخطة الحالي، وتدمج الواجهة مع Worker كوحدة نشر واحدة.
- `workers.dev` يوفر نقطة بدء بلا شراء نطاق.
- تجاوز حصص Workers وD1 المجانية يؤدي إلى فشل أو توقف الخدمة بدل رسوم تجاوز تلقائية.
- D1 علائقي بدلالات SQLite ويلائم العلاقات المالية والتاريخية، مع تصدير SQL.
- Firebase يعالج كلمات المرور والجلسات بدل بناء مصادقة مخصصة عالية المخاطر.
- حصر المزود في Email/Password يمنع إدخال Phone/SMS أو مزود آخر ذي تكلفة أو شروط غير معتمدة.
- البيانات التشغيلية مستقلة عن مزود الهوية وقابلة للنقل.
- قائمة السماح وقيود `app_users` تمنع اعتبار مجرد امتلاك حساب Firebase إذنًا للوصول.

## البدائل المدروسة

- Firebase متكامل: بديل ثانٍ صالح مشروط، لكنه أضعف في SQL والتصدير المدار المجاني.
- Supabase Free: مرفوض بسبب توقف الخمول بعد أسبوع.
- Appwrite Cloud Free: مرفوض بسبب توقف الخمول، وخطر حذف المشروع المتوقف، وعدم وجود backup مجاني.
- Apps Script/Sheets: مرفوض بسبب قيود الهوية الدقيقة وسلامة البيانات.
- Cloudflare Pages: بديل استضافة احتياطي فقط؛ لا يستبدل Workers Static Assets دون قرار لاحق.
- Cloudflare Zero Trust Access: مستبعد لأنه يطلب بيانات دفع في الإعداد حتى على Free.

## النتائج الإيجابية

- تكلفة إلزامية صفرية في حدود الخطط المختارة.
- هوية منفصلة وتفويض دقيق لشخصين.
- نموذج بيانات علائقي ملائم للعمليات المالية والتاريخية.
- تصدير SQL وJSON مفتوح واستعادة قابلة للاختبار.
- مسار مصادقة موثق وفاشل مغلقًا.
- استضافة الواجهة ونقطة البداية محددتان دون اشتراط نطاق مدفوع.

## النتائج السلبية والمخاطر

- تكامل مزودين.
- احتمال عدم ملاءمة تحقق RS256 لحد 10ms، ولذلك توجد بوابة توقف صريحة في S3.
- لا SLA على الخطط المجانية.
- `workers.dev` ملائم كبداية مجانية لمشروع خاص صغير، لكنه ليس التوصية العامة من Cloudflare للأعمال الحرجة.
- النسخ الخارجي يحتاج إجراءً تشغيليًا يدويًا ما لم يعتمد لاحقًا حل مجاني آخر.
- يلزم إعادة التحقق من الخطط والحصص قبل إنشاء أي بيئة فعلية أو نشر.

## قيود الانتقال

هذا الاعتماد لا يجيز:

- إنشاء Cloudflare Worker أو D1 أو Firebase project فعلي دون موافقة مستقلة.
- تفعيل Blaze أو Zero Trust أو Workers Paid أو أي فوترة.
- ربط بطاقة أو Billing Account.
- تفعيل Phone/SMS أو Anonymous أو أي مزود مصادقة غير Email/Password.
- استخدام بيانات حقيقية.
- بدء S3 قبل دمج S2 بعد المراجعة المستقلة.
- تجاوز بوابة CPU في S3.
- دمج PR #17 من جلسة S2.

## دليل التنفيذ في S2

نفذ نموذج محلي يختبر التوقيع والمطالبات وتدوير المفاتيح الوهمي والتخزين حسب `max-age` والفشل المغلق وقائمة السماح والتزامن وسجل التدقيق والتصدير وعدم تخزين ملفات الأعمال. يتضمن الاختبار مسار شهادة X.509 فعلية مولدة مؤقتًا محليًا من نوع `BEGIN CERTIFICATE` عبر `GooglePublicKeyCache`. كما يثبت قيود الحسابين ومصدر المخطط الواحد. تبقى الاختبارات السحابية وقياس CPU ضمن بوابة S3 بعد الموافقات اللازمة.
